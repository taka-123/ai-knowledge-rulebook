# template-guide（backlog-intake-planner 出力雛形）

生成物の責任分界:

| ファイル                    | 位置づけ                                                                   |
| --------------------------- | -------------------------------------------------------------------------- |
| `requirements.md`           | **正本**。Backlog 本文にそのまま貼る。要件・受け入れ条件はここを基準にする |
| `implementation-plan.md`    | 実装補助資料。実装方針・順序・検証観点の参考。正本ではない                 |
| `implementation-handoff.md` | 実装補助資料。AI 実装開始用プロンプト                                      |
| `README.md`                 | Backlog 添付 ZIP 用の説明書（雛形は `handoff-prompt-guide.md`）            |

PR レビューは、`implementation-plan.md` どおりかではなく、**Backlog 本文 / `requirements.md` の受け入れ条件を満たしているか**で判定する。実装者に `implementation-plan.md` との差分報告は求めない。

handoff・README 雛形は `handoff-prompt-guide.md`。実装着手可否チェックは `definition-of-ready.md`（**チャットのみ**。requirements.md には書かない）。

## ブランチ命名規則

| 種別  | パターン                         | 使いどころ                       |
| ----- | -------------------------------- | -------------------------------- |
| feat  | `feat/BUSSW-XXXX-<description>`  | 新機能・新規開発                 |
| fix   | `fix/BUSSW-XXXX-<description>`   | バグ修正・不具合対応             |
| chore | `chore/BUSSW-XXXX-<description>` | 設定変更・整備・リファクタリング |

- `<description>` は英語の kebab-case で10語以内。
- `XXXX` は Backlog 起票後に採番された番号へ置き換える（生成時は `XXXX` のまま）。

出力先: `.work/backlog/BUSSW-AI/{requirements,implementation-plan,implementation-handoff,README}.md`（起票・採番後に `BUSSW-XXXX` へリネーム。plan / handoff / README は深掘り完了時のみ）。

## Backlog 記法（requirements.md 用）

`requirements.md` は Backlog にそのまま貼って崩れない形で出力する。`implementation-plan.md` は対象外（標準 GFM でよい＝Backlog に貼らない前提）。

1. 箇条書きは `* ` を使う（`- ` は使わない）。
2. ネストは**半角スペース4つ**で統一する（タブ・2スペース禁止）。例: `    * 子項目`。
3. チェックリストは `* [ ] ` 形式。
4. 番号付きリストは `1. ` 形式。
5. 見出しは ATX 形式（`#`）。
6. 引用は各行 `> ` で始める。空行は `>` 行で表す。
7. コードはフェンス付きコードブロック（3連バッククォート）。
8. 罫線は `---` に統一する。
9. 強調はアスタリスク（`*italic*` / `**bold**`）。
10. リンクは `[text](url)`、画像は `![alt](url)`（title 属性は付けない）。**url は公開 URL または Backlog チケット URL のみ**。
11. 表は `|` を使う GFM 形式。
12. 定義リスト・`<details>` は通常テキストへ展開する。
13. Backlog 固有記法（`BLG-95`, `[[WikiPage]]`, `#rev(...)`）は保持する。
14. **ローカル参照禁止**: `.work/backlog/...`、`docs/*.md`、相対パスの Markdown リンク、リポジトリ内の作業メモパスを本文に書かない。根拠は「別添PDF」等の添付呼び方か、公開/チケット URL にする。

注意:

- 一般的な Markdown 慣習より、上記規則を優先する。
- 入力に `-` と `*` が混在していても、出力は `*` に統一する。
- Backlog 読者はローカル作業ツリーを持たない前提で書く。

## requirements.md テンプレート

> 記法: 上記「Backlog 記法」節。品質基準: `SKILL.md` の品質基準 2 節。横断の参考例: `.work/backlog/BUSSW-4099/requirements.md`。

```markdown
# [チケットタイトル]

## 対応

* [対象リポジトリ1]
    * （PR URL）
* [対象リポジトリ2]
    * （PR URL）

## 概要

[なぜ・だれが・なにを、を 1〜3 文。読んだ人が「自分の困りごとを正しく理解してくれている」と分かる平易さで]

## 完成イメージ（できるようになること）

- [利用者から見て何ができるようになるか。画面・操作・結果の言葉で]
- [既存の類似機能と同じ範囲まで適用する、と書く場合はその根拠を短く]
- **例外**: [管理者専用・バイパスモードなど、通常と違う挙動があればここに明示]

## やらないこと（スコープ外）

- [今回はやらないこと。期待値のズレを防ぐ]

## 前提（こちらで補った・要確認）

- [推測で補った箇所。確定回答ではない。違えば手戻り]

## 確認したいこと / 未確定

> その場で答えが出ず、誰かに確認が必要な点。**宛先を付けて**まとめて聞ける一覧にする。

- [宛先: 営業・サポート] [質問]
- [宛先: お客さん] [質問]
- [宛先: 社内（エンジニア判断）] [質問]

## 要件（詳細）

- 要件1: [作るものの仕様。対象 repo・画面・入出力を含め具体的に]
- 要件2: [利用側・会員向け等、別 repo がある場合はここで分ける]
- 要件3: [API / 別フロント / 例外モードなど、境界が違う塊は要件番号で分離]

## 受け入れ条件

> 並び順方針: 同じ導線（画面）で確認できる新規項目と `[後方互換]` を連続で並べ、1 往復のテスト操作で複数項目を確認できるようにする。
> PR を作る前に、こちらで動作確認できている状態にする（pre-PR ゲート）。
> 各条件の頭に「通番 / 対象リポジトリ / 要件番号」を付け、確認できた時点でチェックする＝どこまでテストしたかが分かる。
> 開発・検証環境では構造的に検証できない事項は本セクションに含めず、後述「検証環境で確認できない事項」に整理する（チェック項目化しない）。

### [repo] — [機能エリア]（単一 repo・項目が少ない場合は小見出し省略可）

> [モード差・API 経路・バイパス条件など、読者が迷いそうな文脈を 1 行で。不要なら省略]

- [ ] #1 [対象リポジトリ] [要件1] [期待結果を1文で書く]
  - 導線: [実 UI のメニュー名・画面名・タブ名・ボタン名を使った操作経路]
  - 確認: [画面上の何を見れば OK か。導線と分けて書ける場合]
  - 補足: [必要なテストデータ・前提条件・この画面で確認できない代替手段]
- [ ] #2 [対象リポジトリ] [後方互換] [未設定・既存データは従来どおり、を1文で]
  - 導線: [#1 と同じ導線を優先]

### 結合確認（[利用側repo] → [API repo]）（横断時のみ。不要ならセクションごと削除）

- [ ] #N [利用側repo/API repo] [結合確認] [設定・入力が利用画面/API 応答に反映される、を1文で]
  - 導線: [利用者が辿る画面] → [確認対象の操作]
  - 確認対象 API: [呼び出し元] → [エンドポイント・主要パラメータ]
- [ ] #N+1 [repo/repo] [結合確認] [設定側 repo で保存した値が利用側に効く]
  - 導線: [設定画面で保存] → [利用画面で候補・表示を確認]

### [repo] — [別機能エリア]

- [ ] #N [対象リポジトリ] [要件2] [期待結果を1文で書く]
  - 導線A: [入口1からの操作経路]
  - 導線B: [入口2からの操作経路]
  - 確認: [導線A/B 共通で見るべき表示・選択可否]
- [ ] #N+1 [API repo] [要件3] [UI 導線がない場合]
  - 確認方法: [エンドポイント・入力条件・期待レスポンス]

## 検証環境で確認できない事項（無ければセクションごと削除）

> サンドボックス API・本番限定の外部依存・意図的なエラー注入が必要な経路など、開発・検証環境では構造的に検証できない事項を整理する。
> PR 前ゲートでは検証できないため、コードレビューと、本番運用開始後の初回稼働ログ確認で担保する。
> 本セクションはレビュー観点を絞り込むことを意図せず、「検証できる範囲を明確化する」ことが目的（レビュー観点は「影響範囲・レビュー観点」を参照）。

- [要件x] [再現できない事象] / [コード根拠・本番カナリアで担保する旨]

## DB変更（無ければ「なし」と書く）

> テーブルごとにサブ見出しを立て、その下に変更カラムを書く（テーブル名を列に混ぜない）。

### [テーブル名]（新規作成 / カラム追加 など）

| カラム   | 型 / 制約           | 内容   |
| -------- | ------------------- | ------ |
| [カラム] | [型・NULL・DEFAULT] | [用途] |

## 影響範囲・レビュー観点

> 影響リポジトリは、PR 前セルフレビュー（`pr-self-reviewer`）が対象 repo を特定する正規の情報源になる。`htdocs/` 配下の**実際のディレクトリ名**で正確に書く（例: `sc` / `sc_ddl` / `ScSbPaymentTransfer`）。横断する場合は該当 repo をすべて列挙する。

- 影響リポジトリ: [例: sc / sc_ddl / ScSbPaymentTransfer]
- 特に見てほしい観点: [例: 認可漏れ / 既存 API の後方互換 / 計算ロジックの正しさ]

## 用語（非エンジニアに馴染みのない語がある場合のみ。無ければセクションごと削除）

| 用語   | 定義         |
| ------ | ------------ |
| [用語] | [平易な定義] |
```

書き方の指針:

- 前半は非エンジニアが合致確認できる言葉、後半は実装・レビュー向け。同じ内容を同粒度で二度書かない。
- `## 対応` は実装対象リポジトリごとに枠を用意する。
  - 生成時点で分かっている repo を列挙し、各 repo の下に `（PR URL）` を置く（単一 repo でも 1 件）。
  - 未確定なら `* （影響リポジトリ確定後に列挙）` とし、深掘りで埋める。
  - 深掘り後は「影響範囲・レビュー観点」の影響リポジトリと一致させる。
  - PR 作成後は `（PR URL）` を実 URL（または `[PR #n](url)`）へ置き換える。
- 受け入れ条件のルール詳細は `SKILL.md` の「受け入れ条件の品質基準」が正本。本ファイルは雛形と例を提供する。

### 粒度の出し分け

| 課題                           | 書き方                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| 単一 repo・画面 1〜2           | 小見出しなしのフラット列で十分                               |
| 同一 repo で機能エリアが複数   | `### sc — 振替` のように機能で小見出し                       |
| 設定 repo + 利用 repo          | 設定・利用を分け、横断は `結合確認` セクション               |
| フロント + API（scr + scp 等） | **結合確認** を優先（単体 repo テストで終わらせない）        |
| 例外・バイパスモード           | `完成イメージ` の **例外** と、通常/例外で受け入れ条件を分離 |

導線・横断確認の例:

```markdown
### sc — 予約枠設定

- [ ] #1 [sc] [要件1] 編集画面で対象の値を保存でき、再表示で保持される
  - 導線: 管理画面右上の歯車アイコン → 受講 → スクールマスタ → 予約枠 → 対象枠の編集
- [ ] #2 [sc] [後方互換] 既存枠を開いたとき、未設定項目は初期値どおり表示される
  - 導線: 管理画面右上の歯車アイコン → 受講 → スクールマスタ → 予約枠 → 既存枠の編集

### sc — 振替先選択（月／週）

- [ ] #3 [sc] [要件2] 条件に合わない枠は選択できない
  - 導線: 利用者 → 生徒一覧 → 出欠状況 → 振替先を選択 → 月表示・週表示
  - 補足: 凡例がない画面は、枠ヘッダ表示と選択不可で確認する

### 結合確認（scr → scp API）

> scr 公開体験は scp API 経由。scr 単体の表示だけでは不十分。

- [ ] #4 [scr/scp] [結合確認] 条件に合う枠だけ候補に表示され、不一致送信は scp 側で弾かれる
  - 導線: 体験一覧 `/trial/list?f=<facility>` → 体験に申し込む → 性別変更 → 候補更新 → 申込
  - 確認対象 API: scr `store/trial.js` → scp `/api_trial/get_trial_date`, `/api_trial/register`
- [ ] #5 [sc/scp/scr] [結合確認] 施設側で設定した値が公開体験の候補に反映される
  - 導線: [sc で設定保存] → 体験一覧 → 体験に申し込む
```

単一 repo の最小例（小見出し省略）:

```markdown
- [ ] #1 [scnm] [要件1] 対象画面で期待どおり表示・操作できる
  - 導線: [メニュー] → [画面] → [操作]
- [ ] #2 [scnm] [後方互換] 既存データは従来どおり動作する
  - 導線: [同上]
```

## implementation-plan.md テンプレート

> 記法: 標準 GFM。品質基準: `SKILL.md` の「implementation-plan.md の品質基準」。正本は `requirements.md`（本ファイルは雛形）。

```markdown
# 実装計画: [機能名]

> 関連チケット: BUSSW-XXXX ／ 正本は Backlog 本文（≒ `requirements.md`）。本ファイルは実装補助資料。

## 0. 着手ブロッカー（実装前に確定すること）

> 埋まらないと途中で詰まる。着手前に必ず解消する。無ければ「なし」。

- [ ] [未確定の repo・仕様・依存 ＋ どう確定するか（誰に聞く／何を調べる）]

## 1. 方針

[採用する作り方と理由を数行。なぜ他案でなくこれか]

## 1.5 参考にする既存実装（あれば）

> 似た既存実装があれば、**具体的なファイル・クラス・メソッド名**まで書く。「既存を参考」で止めない。実装者がどこを読めばいいか即分かる状態にする。

- [対象（UI / ロジック等）]: `[ファイルパス]` の `[クラス/メソッド]` — [何を参考にするか]

## 2. データモデル（DB変更がある場合のみ）

### テーブル: [名前]

| カラム | 型         | NULL | 説明   |
| ------ | ---------- | ---- | ------ |
| id     | biginteger | 不可 | 主キー |

- 制約・インデックス・監査カラム（created/modified 等）を明記

## 3. インターフェース／契約（境界をまたぐ場合のみ）

> API・画面とサーバ間・サービス間・関数の入出力など、実装が依存する契約を確定させる。

### API / エンドポイント

| エンドポイント | メソッド | リクエスト | レスポンス | 認可   |
| -------------- | -------- | ---------- | ---------- | ------ |
| `/api/[path]`  | POST     | [項目]     | [項目・形] | [条件] |

### 関数 / イベント（該当時）

- [シグネチャ・入出力・前提]

## 4. 制御ルール・エッジケース・制約（曖昧さの排除）

- 制御ルール: [冪等性 / 計算ロジック / 状態遷移など、実装中に迷う分岐]
- エッジケース: [0 件・大量データ・同時実行・権限差]
- 制約: [セキュリティ（認可・データ保護） / 性能（N+1・インデックス） / 後方互換（既存への影響）]

## 5. 実装ステップ（スプリント計画）

> このまま上から実行すれば完成する粒度。各ステップに「対象・やること・完了の確認方法」を必ず付け、§2〜4 を参照させる。

| #   | 対象（repo / 領域） | やること                        | 完了の確認方法（requirements #n）    | 依存 |
| --- | ------------------- | ------------------------------- | ------------------------------------ | ---- |
| 1   | [repo]              | [作業（§2 のテーブル等を参照）] | [受け入れ条件 #n または検証コマンド] | -    |
| 2   | [repo]              | [作業（§3 の契約に沿う）]       | [〃]                                 | 1    |

## 6. 検証ゲート（完了判定）

- [ ] lint / build が通る
- [ ] requirements.md の受け入れ条件をすべて満たす
- [ ] （危険領域）reviewer の Verdict: ready
- [ ] （schema 変更）`sc-ddl-migration-impact` の結果を添付

## 7. 見積もり

| ステップ | 工数       |
| -------- | ---------- |
| **合計** | **[合計]** |
```

書き方の指針:

- §2〜4 で実装判断を先に確定し、§5 から参照する。ステップ列だけにしない。
- §1.5 はファイルパス＋クラス/メソッドまで。§5 の完了確認は `requirements.md` の #n と対応させる。
